# v1.0 Milestone Audit — Career Quest (Session 1 Completion)

**Audited:** 2026-07-24
**Status:** ⚠ gaps_found

## Verdict

All 4 phases executed and every phase VERIFICATION.md passed its **in-isolation** checks. But the milestone's core value — *a student completes Session 1 end-to-end and their progress is reliably saved* — **does not work in a live session**. The break sits precisely on the load-bearing seam between Phase 1's confirmatory-round reducer logic and Phase 2's completion UI, which is exactly the gap that per-phase verification cannot see.

Two independent critical defects, both verified directly against the source:

### 🔴 Critical 1 — The entire completion/persistence experience is dead code

`RevealSequence`'s tail states (`badge_unlock → comparison_hint → session_complete → CompletionScreen`) are structurally unreachable. `handleNext`'s `sequence` array ends at `confirmatory_intro`, which calls `onRevealComplete()` → `dispatch(ENTER_CONFIRMATORY)` → `flowPhase` becomes `"confirmatory"` → `<RevealSequence>` (rendered only when `flowPhase === "reveal"`) unmounts. Nothing anywhere calls `setPhase("badge_unlock")`, the only entry into that tail.

After the confirmatory questions, `flowPhase` goes straight to `"complete"` (reducer `ANSWER_CONFIRMATORY`, use-quest-state.ts:344/353), rendering a **static** screen (page.tsx:619) that says *"Quest progress saved!"* while calling **no persistence whatsoever**. All three `runFinalPersist` callers (`handlePersistStart`, `handleRetryPersist`, `handleSaveExit`) are wired only to the unreachable `CompletionScreen`.

**Consequence:** `has_completed_session1`, `session_responses`, and `assessment_scores` are never written at the end of a session. Confetti, Save & Exit, PersistenceBanner, `validateScoresBeforePersist`, and `classifySupabaseError` are all individually correct and unit-tested but never execute. This is a regression from commit `f43d177`.

**Breaks:** COMP-02, COMP-03, COMP-04, DATA-01, DATA-02, DATA-03.

### 🔴 Critical 2 — Dashboard student query uses a non-existent column

`app/quest/dashboard/page.tsx:97` uses `.eq("user_id", user.id)`, but the `students` table PK is `id` (migration `00001_initial_schema.sql`). Every other query in the app correctly uses `.eq("id", ...)`. `studentRes.data` is always `null`, so the dashboard shows its empty "No results yet" state for **every** student. Even if Critical 1 is fixed, the returning-student dashboard stays empty.

**Breaks:** the read side of COMP-03 and the whole returning-student dashboard.

## Recommended Gap Closure (priority order)

1. **Reconnect the completion flow.** Either (a) move `CompletionScreen` rendering + `handlePersistStart` into the `flowPhase === "complete"` branch (page.tsx:619), or (b) route `ANSWER_CONFIRMATORY` isLast back through `flowPhase: "reveal"` with `RevealSequence` set to `session_complete`. Ensure `runFinalPersist` fires exactly once on entry to the completion screen. — closes COMP-02/03/04, DATA-01/02/03, AUDIT-04.
2. **Fix dashboard query:** `dashboard/page.tsx:97` `.eq("user_id", …)` → `.eq("id", …)`. — closes COMP-03 read side.
3. **SCORE-01 for returning students:** persist raw per-dichotomy MBTI counts, or pass counts to `deriveEmergingType` on the dashboard, or document the degradation as an accepted limitation.
4. **AUDIT-01 hygiene:** add `.claude/worktrees/**` to `vitest.config.ts` exclude.
5. **Run the deferred human-verification checks** from phases 01 and 02 once 1–2 land — these are the browser walkthroughs that would have caught this originally.
